# План Code Review — Вариант А (Банковское приложение)

## Раздел 1. Цели ревью
* Обеспечение максимальной безопасности модуля авторизации.
* Проверка соответствия обработки персональных данных закону 152-ФЗ.
* Исключение утечек логинов, паролей и сессионных токенов.

## Раздел 2. Критерии оценки кода
* Отсутствие открытого логирования конфиденциальных данных.
* Корректная инвалидация токенов при выходе (logout).
* Покрытие кода юнит-тестами для проверки двухфакторной аутентификации (2FA).

## Раздел 8. Разрешение споров и эскалация
### 1. Правило "Двух голосов"
Поскольку наша команда состоит из 3 человек (Автор кода, Рецензент 1, Рецензент 2), при возникновении архитектурных разногласий финальное решение принимается путем голосования большинства. Если Рецензент 1 требует изменить архитектуру функции, а Рецензент 2 считает текущий вариант оптимальным, проводится короткое обсуждение. Если компромисс не найден, решающий голос остается за Тимлидом (или третьим участником команды, не вовлеченным в написание данного кода). Автор кода обязан подчиниться решению большинства.

### 2. Эскалация (Критические уязвимости безопасности)
Если спор касается потенциальной критической уязвимости безопасности (обработка персональных данных по 152-ФЗ, хранение паролей или токенов сессий), а Автор кода не согласен с замечанием рецензента, обсуждение внутри команды прекращается. Вопрос незамедлительно эскалируется на уровень CISO (Директора по информационной безопасности) или Главного архитектора банка. Код не может быть слит в ветку develop без официального письменного апрува или резолюции от ИБ-департамента.

### 3. Время на дискуссию
На обсуждение одного спорного комментария в Pull Request внутри команды выделяется не более 2 часов в асинхронном режиме (в комментариях к PR или рабочем чате). Если по истечении этого времени консенсус не достигнут, авторы спора обязаны созвониться на 15-минутный синхронный звонок. Если и после звонка решение не принято, ветка спора немедленно эскалируется на уровень выше.
